# 평가 결과

## 2단계: 임베딩 모델 비교 (2026-07-09)

### 방법
- `backend/data/eval/test_queries.json`: 실제 케이스 기반 시나리오 + 병무청 FAQ 스타일 질문 15개
  (질문 → 정답 조항 `law_name`/`article_no`/`paragraph_no` 라벨링), 그 중 1개(id=15, 카투사)는
  의도적 스코프 밖 네거티브 테스트
- 후보 3개 모델로 272개 청크 + 15개 질문 임베딩 후 cosine similarity로 Recall@5, Recall@10, MRR 계산
  (`backend/evaluation/compare_embeddings.py`)

### 결과

| 모델 | Recall@5 | Recall@10 | MRR | 긍정 평균 top1 | 부정(카투사) top1 |
|---|---|---|---|---|---|
| **BGE-m3** | 0.929 (13/14) | **1.0 (14/14)** | 0.746 | 0.723 | 0.443 |
| multilingual-e5-large | 0.929 (13/14) | 0.929 (13/14) | **0.816** | 0.887 | 0.801 |
| KoE5 | 0.857 (12/14) | 0.929 (13/14) | 0.612 | 0.694 | 0.264 |

### 선정: BGE-m3

- Recall@10 만점(14/14)이고, 긍정/부정 질문 간 유사도 점수 구분이 가장 뚜렷함
  (multilingual-e5-large는 스코프 밖 질문에도 top1 유사도 0.801을 줘서 절대 점수만으로
  "관련 조항 없음"을 판단하기 어려움)
- 부가 이점: BGE-m3는 dense + sparse(lexical weight) 임베딩을 한 모델에서 함께 뽑을 수 있어,
  3단계 BM25+Dense 하이브리드 검색 구현 시 참고 가능
- KoE5(한국어 특화 모델)가 오히려 가장 낮은 성능 — 이 규모(560M) 모델 간 우열은
  "한국어 특화 여부"보다 retrieval contrastive 학습 방식/데이터 품질 차이가 더 크게 작용하는 것으로 보임

### 시사점: 하이브리드 검색(3단계)의 필요성 실증

- 질문 14번("국외여행허가 없이 계속 출국을 미루면 어떤 불이익이 있나요?")의 정답 조항
  (병역법 제70조 제2항)은 본문에 "기피"라는 단어가 그대로 들어있는데도, **3개 모델 전부 top-5를
  놓침** (순위 9~19위). Dense 임베딩만으로는 이런 어휘 일치 케이스를 놓칠 수 있어,
  BM25(어휘 매칭)를 병행하는 하이브리드 설계가 실제로 필요하다는 근거가 됨.

### 인프라
- MongoDB Atlas Vector Search 인덱스(`law_chunks_vector_index`, cosine, 1024차원)에 272개 청크
  전체를 BGE-m3로 임베딩하여 적재 완료. `$vectorSearch` 실제 쿼리로 검증함
  (`backend/pipeline/load_to_mongo.py`).

## 3단계: Hybrid Retrieval + Reranker (2026-07-10)

### 방법
- BM25는 `kiwipiepy`로 형태소 분석 후 조사/어미를 제거한 명사/동사 어간만 인덱싱
- Hybrid: BM25 + Dense(BGE-m3) 점수를 각각 min-max 정규화한 뒤 `alpha * dense + (1-alpha) * bm25`로
  가중합. `alpha`는 0.0~1.0을 0.1 단위로 그리드서치 (`backend/evaluation/tune_hybrid.py`)
- Reranker: 하이브리드 top-30 후보를 BAAI/bge-reranker-v2-m3로 재정렬

### 결과 (test_queries.json 14번 문항 라벨 수정 후 기준)

| 구성 | Recall@5 | Recall@10 | MRR | 부정(카투사) top1 |
|---|---|---|---|---|
| BM25 단독 | 1.0 | 1.0 | 0.818 | (점수 스케일 달라 비교 무의미) |
| Hybrid (`alpha=0.3`, BM25 70% + Dense 30%) | **1.0** | **1.0** | **0.929** | (정규화 점수라 해석 어려움) |
| Hybrid + Reranker | 1.0 (top-3 기준) | — | 0.881 | **0.000** |

### 관찰

- **BM25 단독이 이미 매우 강력함** (Recall@5/10 = 1.0). 이 프로젝트 도메인(병역법 Q&A)은 사용자
  질문과 법조문이 어휘를 상당히 공유하기 때문으로 보임.
- **Reranker는 Recall/MRR을 더 올리진 못했지만** (샘플이 14개뿐이라 노이즈 수준의 차이),
  **점수의 해석 가능성에서 결정적으로 유리함**: 실제 정답 질문엔 0.77~0.999, 스코프 밖 질문(카투사)엔
  0.000을 줘서 "관련 조항 없음" 판단에 쓸 수 있는 신뢰도 점수를 제공함. 2단계에서
  multilingual-e5-large가 이 구분을 못했던 문제를 reranker가 해결.
- **검증 과정에서 테스트셋 라벨 오류 하나를 발견**: 14번 문항("출국을 미루거나 기피하면 어떤
  불이익")의 정답을 원래 병역법 제70조 제2항으로만 라벨링했는데, hybrid+reranker가 계속 병역법
  제94조(국외여행허가 의무 위반 — 실제 처벌조항)를 1순위로 반환해서 확인해보니 그게 더 정확한
  답이었음. 라벨을 수정(`제94조` 추가)한 뒤 재검증함.

## 4단계: Intent Classifier 검증 (2026-07-10)

- Rule-based 키워드 매칭(`classifier/predict.py`)을 test_queries.json 15문항에 대해 검증
- 명시적으로 키워드가 포함된 질문은 정확히 분류됨. 구어체 표현(예: "미룰 수 있나요" → "연기"
  키워드 없음)은 동의어를 추가해 대응
- 암묵적 문맥이 필요한 케이스(예: 이전 대화에서 언급된 사용자 유형이 후속 질문엔 없음)는 규칙
  기반 분류기의 근본적 한계로 남겨둠 — 계획대로 데이터가 쌓이면 경량 분류기로 교체 예정
- 카투사 등 스코프 밖 키워드 매칭 시 `out_of_scope=True` + fallback 안내 문구 반환 확인함

## 프로토타입 검증: "입영연기" 태깅·랭킹 오류 진단 및 수정 (2026-07-10)

Flask API(`app.py`, `routes/query.py`) + 정적 HTML 프로토타입(`frontend/prototype.html`)을 붙여서
실제 질문으로 테스트하던 중 발견/수정한 이슈.

### 문제 1: "연기" 토픽 태그의 방향성 부재

`영주권자인데 입영연기 어떻게 하나요` 질문에 "병역연기 처분을 **취소**한다"는 정반대 의미의
조항(국외여행 업무처리 규정 제24조, 영주권자 등 입영희망신청제도 — 자진 조기입영 절차)이
최상위로 뜨고, 정작 답이어야 할 시행령 제128조/149조/별표3은 아예 후보에 없거나 하위권.

**원인 진단:**
- `tagger.py`(정확히는 공유 테이블 `classifier/model.py`)가 단순 문자열 포함 여부로만 "연기"
  태그를 붙이고 있었음
- 청크 텍스트 맨 앞에 `[법명 제70조(국외여행의 허가 및 취소) 제N항]` 헤더가 붙는데, 제목 자체에
  "취소"가 들어있어서(예: 병역법 70조) 그 조의 모든 항이 실제 내용과 무관하게 "연기+취소" 동시
  출현으로 오염됨
- 더 근본적으로: intent classifier가 계산한 태그가 실제 검색 랭킹(hybrid+reranker)에 전혀
  반영되지 않고 화면 표시용 메타데이터에 그치고 있었음 — 태그를 아무리 정교하게 고쳐도 검색
  결과 자체는 바뀌지 않는 구조였음

**수정:**
- "연기" 토픽을 `입영연기_신청`(허가로 인해 연기되는 근거) / `입영연기_취소`(연기 처분 자체가
  취소·철회되는 조항) 두 방향으로 분리
  - 코퍼스 쪽: 정규식 `연기(를|처분을|처분의|처분과|의)?.{0,25}?취소`로 "연기 처분 자체가
    취소되는" 케이스만 정밀 매칭(6건) — 단순 "연기"+"취소" 동시출현(39건)보다 훨씬 좁게 잡아서
    70조/147조의2 같은 "허가취소"(처벌성 취소, 별개 개념)를 오분류하지 않음
  - 국외여행 업무처리 규정 제24조는 본문에 "연기...취소" 문구가 없는 항도 있어서, 제목에
    "입영희망"이 있으면 무조건 `_취소`로 태깅하는 규칙 추가 (이 조 전체가 "자진 조기입대 =
    기존 연기 포기"라는 성격이라 제목 자체가 강한 신호)
  - 질문 쪽은 "취소/철회/그만두고 싶다" 등 부정 표현이 있으면 `_취소`, 없으면 기본 `_신청`
- `routes/query.py`에 실제 가중치 반영: 후보 폭 30→50 확장(128조가 원래 후보 30위 밖에 있었음),
  리랭커도 top-5가 아니라 top-15까지 본 뒤 intent 방향과 청크 방향 일치 시 +0.25, 불일치 시
  -0.25 보정 후 최종 top-5 선정

**재검증 결과:**
- "영주권자인데 입영연기 어떻게 하나요" → 병역법 시행령 제128조 제2항이 1위로 (기존: 후보에도
  없었음), 제24조(취소 방향)는 4위로 밀림
- "영주권자인데 입영연기 취소하고 싶어요" (반대 방향) → 제24조가 정확히 1~3위 부스트됨
- "영주권 취득한 지 3년 넘었는데 몇 살까지 국외여행허가 받을 수 있나요?" (거주기간 조건이 명시된
  질문) → 별표3이 top-5를 전부 차지. 즉 "일반 절차 질문 → 128조", "구체적 기간 조건 질문 → 별표3"
  으로 정상 분기됨을 확인 (별표3이 첫 번째 일반 질문에서 안 뜬 건 버그가 아니라 정상 판단이었음)

### 문제 2: 스코프 밖(카투사 등) fallback을 인접 정보로 유도

기존엔 카투사/어학병 키워드 감지 시 "법령 DB에 없다"는 안내만 반환. 유저 타입(영주권자/유학생
등)이 같이 감지되면, 실제로 답변 가능한 인접 정보(제24조 영주권자 등 입영희망신청제도 — 자진
조기입영 절차)로 유도하도록 개선. `classify()`가 `related_lookup`(법명+조번호)을 반환하면
`routes/query.py`가 해당 조항 전체를 직접 조회해서 `related_scope_info`로 같이 내려줌. 유저
타입이 감지 안 되면 조항 조회 없이 일반 재질문 유도 문구만 반환.

테스트: "카투사(KATUSA)로 배치받으려면..." (유저타입 없음) → 일반 안내만, `related_scope_info: null`.
"카투사 지원하고 싶은데 영주권자도 되나요?" (유저타입 감지) → 영주권자 맞춤 안내 + 제24조 9개
항 전체를 `related_scope_info`로 반환, 둘 다 의도대로 동작 확인.

## 검색 파이프라인 품질 개선 2차: 6개 이슈 진단 및 수정 (2026-07-10)

### 이슈 5 (최우선 처리): 조문 경계 파싱 버그 — 272개 청크 재스캔

**증상**: `병역의무자 국외여행 업무처리 규정` 제21조 청크에 실제로는 제21~23조 세 조문이
경계 구분 없이 병합되어 있음 (`...재학하는 경우제22조(영리활동의 범위)...`처럼 공백 없이
이어붙음).

**전수 스캔**: `제\d+조(?:의\d+)?\([^)]+\)` 패턴이 청크 본문에 2회 이상 나타나는 청크를
찾은 결과 **272개 청크 중 16개 오염 확인** (대부분 국외여행 업무처리 규정에 집중, "제30조"
라벨 청크는 3개나 존재하며 서로 다른 내용을 담고 있었음).

**근본 원인**: 원인은 예상(항 번호 없는 단일 블록 조문에서 다음 조 헤더 인식 실패)과 달리,
**1차 세션에서 만든 `join_wrapped_lines()`(PDF 줄바꿈 중간에 끊긴 단어 복구용)가 조문 경계의
정당한 줄바꿈까지 지워버린 부작용**이었음. 원본 PDF엔 "...재학하는 경우\n제22조(영리활동의
범위)..."로 정상적으로 줄바꿈이 있었는데, "한글+줄바꿈+한글" 패턴이면 무조건 붙이는 로직 때문에
조문 경계가 사라짐.

**수정**:
1. `join_wrapped_lines()`에 "제N조(" 패턴 앞의 줄바꿈은 붙이지 않는 예외 추가 → 16건 중
   15건 해소
2. 남은 1건("병역법 시행령 제156조" 청크)은 별개 원인 — 본문 목록 항목이 "법 제46조(법
   제54조제1항에서 준용하는 경우를 포함한다)"처럼 다른 조항을 인용하면서 우연히 헤더 패턴과
   일치. `article_pattern`에 "괄호 안 내용이 '제N조'를 포함하면 제외" 필터 추가로 해결
   (실제 조문 제목 중 자기 안에 "제N조"를 포함하는 사례는 없음을 확인 후 적용)
3. 재파싱 후 272개 → **270개 청크**로 변경 (개별 조문이 정확히 분리되면서 단락 길이 기준
   500자 재분할 경계가 바뀐 결과). 21/22/23조가 각각 1개씩 정확히 분리됨을 확인
4. 재태깅 → BGE-m3로 재임베딩 → MongoDB Atlas 재색인 완료

이 수정은 이슈 3(동의어 갭)의 재현 여부에도 영향을 줄 수 있어 이슈 3 작업 전에 먼저 처리함.

### 이슈 1: 정답 데이터가 있는데 검색이 못 찾음 — 앵커 강제포함 + 명시적 부스트

**진단**: `국외여행 업무처리 규정 제27조③`("재학사실을...확인한 결과 허가요건을 유지하지
못한 경우" → 허가취소)이 "휴학"/"자퇴" 질문의 정답인데, 두 단어가 본문에 전혀 등장하지 않음.
- "유학 중인데 휴학하면 입영연기가 취소되나요" → BM25 순위 2위(6.12점, 1위 6.42점과 근소) —
  나쁘지 않음
- "외국 대학 자퇴하면 병역은 어떻게 되나요" → BM25 순위 **168/270위**(1.19점, 1위 11.69점) —
  사실상 실종

**1차 시도(실패)**: `SYNONYM_ANCHOR_LOOKUPS`로 "휴학/자퇴/제적" 감지 시 27조 청크를 후보

1. `reranker.rerank()`를 top-15가 아니라 **후보 전체**에 대해 점수를 매기도록 변경 (그래야

### 이슈 2: Threshold 재확인 — 절대 점수만으론 노이즈/정답 구분 불가능함을 확인

**진단**: threshold 로직이 실제로 전혀 구현되어 있지 않았음 (코드 확인으로 확정).

**점수 분포 실측** (재랭커 top-1 점수, 이슈 5 수정 후):

| 케이스 | 점수 | 비고 |
|---|---|---|
| 사회복무요원 해외 (정답) | 0.9882 | 명확히 높음 |
| 아빠 주재원 (정답) | 0.1086 | |

**핵심 발견**: 정답 케이스(0.0061, 0.0073)가 노이즈 케이스(0.0147)보다 오히려 **낮은 점수**를
받는 역전이 있어서, **단일 절대 threshold로는 이 둘을 깔끔하게 분리할 수 없음**이 실측으로
확인됨. 원인은 재랭커가 짧고 불완전한 문장(질문형이 아닌 진술문)에 낮은 점수를 주는 경향과,
노이즈 케이스도 어휘가 일부 겹치면 우연히 조금 더 높은 점수를 받을 수 있기 때문으로 추정.

**구현**: 위 사실을 반영해서 하드 컷오프(결과 숨김)가 아니라 **어드바이저리 방식**으로 구현.
`LOW_CONFIDENCE_THRESHOLD = 0.05` 미만이면 `low_confidence: true` + 재질문 유도 문구를
추가하되, 검색 결과 자체는 그대로 노출 (약한 신호의 정답까지 숨기는 것을 방지). 이 임계값은
정답을 오탐(과소 확신 표시)하는 경우가 있음을 인지하고 있으며, 더 나은 신호(예: 5단계 Claude
API 연동 후 LLM 기반 관련성 재검증)가 필요한 영역으로 남겨둠.

## Threshold 개선 검증: margin(top1-top2) 기반 저신뢰 판정 (2026-07-15)

### 배경

이슈 2에서 절대 점수 하나만으로는 정답/노이즈를 깔끔히 분리할 수 없음을 확인했다
(정답 케이스 0.0061이 노이즈 케이스 0.0147보다 낮은 역전 현상). 가설: top-1과 top-2
점수의 **격차(margin)** 가 절대 점수보다 신뢰할 만한 신호일 수 있다 — 진짜 정답이면
1위가 2위를 크게 앞서고, 노이즈성 결과는 다들 고만고만하게 낮은 점수를 받을 것이라는
추론이다.

`routes/query.py`에 reranker 직후(directional/anchor boost 적용 전) margin 로깅을
추가하고, 최종 12개 재검증 쿼리를 다시 돌려 값을 수집했다.

### 가설 검증

**강한 TP (1, 4, 5, 9, 11)**: margin이 0.03~0.16대로, 노이즈 케이스(0.0004~0.0006)와
확실히 구분된다. 다만 이 케이스들은 절대 점수 자체가 이미 0.05 threshold를 넘겨서
`low_confidence=False`로 정상 분류되고 있었다 — margin이 없어도 기존 로직으로 충분했다.

**절대 점수가 이슈였던 저신뢰 구간 (2, 3, 7, 8, 10 — 모두 절대 점수 < 0.05)**: 이 구간
안에서는 margin으로 순서를 매기면 노이즈(#3=0.0004, #7=0.0006)가 정답(#10=0.0008,
#8=0.0014, #2=0.0046)보다 항상 낮게 나왔다 — 방향은 가설과 일치한다. 특히 애초에 이
검증을 촉발한 역전 케이스(#10 vs #7)를 margin 기준으로 다시 보면, 절대 점수는
0.0061 < 0.0147로 거꾸로였지만 margin은 0.0008 > 0.0006으로 **순서가 바로잡힌다**.

**그러나** 이 구간에서의 margin 격차 자체가 0.0002~0.0010 수준으로, 절대 점수와 마찬가지로
매우 작다. 노이즈 샘플이 2개(#3, #7)뿐이고 #10과 #7의 margin 차이가 0.0002에 불과해서,
이 12개 쿼리만으로 "margin 0.0007 이상이면 정답"같은 하드 threshold를 확정하는 건
과적합 위험이 크다 — 리랭커를 재학습하거나 쿼리 표현이 조금만 달라져도 이 순서가 다시
뒤집힐 수 있는 폭이다.

### 결론 및 다음 액션

가설의 **방향은 지지된다** (노이즈 margin이 정답 margin보다 작고, 문제가 됐던 역전
케이스도 바로잡힘) — 하지만 강한 TP를 걸러내는 데는 margin이 기존 절대 threshold 대비
추가 이득이 없고, margin이 실제로 필요한 저신뢰 구간에서는 격차가 너무 얇아서(0.0002
수준) 5~7개 샘플만으로 실전 threshold를 걸기엔 근거가 부족하다. 지금 `low_confidence`
로직에 margin 조건을 코드로 반영하는 건 보류한다.

### 증상

### 진단
1. **law_chunks.json 자체는 최신 상태였음** — 청크 270개, mtime이 최근 재파싱 시점과 일치.

   계속 떠 있었다면 파일 수정 시 자동 재시작됐어야 함.
3. **실제 원인으로 추정되는 것: 좀비/중복 프로세스.** 이번 세션에서 재시작을 반복하면서

   **2개 동시에** 떠 있는 게 확인된 적 있음(Werkzeug reloader가 부모 감시 프로세스 + 자식 워커
   프로세스 구조라, 포트를 문 자식만 죽이고 부모가 남아있으면 재시작 루프가 꼬일 수 있음).
   구버전 코드를 로드한 채 남아있던 프로세스가 요청을 처리했을 가능성이 높음.
4. **재현 확인 시도**: 이번 확인 시점엔 애초에 포트 5001에 아무 프로세스도 떠 있지 않았음

   `pkill -9 -f "app.py"`(포트가 아니라 프로세스명 기준, 좀비까지 확실히 정리)로 완전히 클린한

## 이슈 B 수정: `low_confidence` 플래그가 프론트에 표시되지 않음 (2026-07-31)

### 증상

`routes/query.py`는 `low_confidence: true`일 때 재질문을 유도하는

않아 화면에 아무 표시도 되지 않았다. 그 결과 관련도가 노이즈 수준(예:
raw score 0.0007)인 결과도 확정 답변처럼 보이는 문제가 있었다.

### 수정

`frontend/prototype.html`에 두 가지 변경:

1. `<style>`에 `.low-conf` 클래스 신설 — 기존 `.oos`(스코프 밖 안내, 주황 톤)와

   분기를 모두 통과한 뒤), `data.low_confidence && data.low_confidence_notice`일
   때만 `escapeHtml`을 거친 `.low-conf` 안내 박스를 삽입.

```javascript
if (data.low_confidence && data.low_confidence_notice) {
  html += `<div class="low-conf">${escapeHtml(data.low_confidence_notice)}</div>`;
}
```

결과로 정상 렌더링됨을 확인했고, 고신뢰 케이스에서 오탐 없음, 악성 페이로드도

## Stage 5: Gemini Flash 답변 생성 검증 (2026-07-31)

### 배경

Anthropic Claude API에서 Google Gemini API로 전환(사유는 `docs/devlog.md` 참고)한
뒤, 검색된 근거조항 + 질문 → grounding된 citation 포함 답변 생성 기능을 새로
구현하고 검증했다. 판단(어떤 조항이 관련 있는지, 신뢰도)은 이미 4단계까지의
rule-based 파이프라인이 전담하므로, 이 기능의 유일한 책임은 이미 검색된 텍스트를
근거로만 답변을 종합하는 것이다.

### 1~2단계: 비용 안전장치 + `generate_answer()` 모듈

- `backend/generation/gemini_client.py`: 6개 모델 화이트리스트(`gemini-3.6-flash`,
  `gemini-3.5-flash`, `gemini-3.5-flash-lite`, `gemini-3.1-flash-lite`,
  `gemini-2.5-flash`, `gemini-2.0-flash`) 하드코딩, 화이트리스트 밖 모델명은
  `DisallowedModelError`로 API 호출 자체를 막음. `vertexai=False` 명시(Google AI
  Studio 경로만, 과금 전제인 Vertex AI 미사용). 429(rate limit/quota) 에러만
  최대 2회 exponential backoff 재시도, 그 외 에러는 즉시 전파. 데이터 프라이버시
  참고사항(무료 티어 프롬프트가 Google 제품 개선에 활용될 수 있음)을 코드 주석으로
  남김.
- `backend/generation/answer.py`: `generate_answer(question, results)` —
  grounding을 강제하는 system_instruction("근거조항에 없는 내용은 추측하거나
  지어내지 말 것", "제공된 조항만으로는 판단하기 어렵다"고 명시하도록 지시) +
  citation 형식("○○법 제○○조 제○항에 따르면") 강제 지시. `results`가 비어있으면
  `None` 반환(방어적 가드). **`low_confidence` 분기는 이 함수가 아니라
  `routes/query.py`가 담당** — `generate_answer()`는 애초에 `low_confidence`
  플래그를 받지 않도록 설계해서, 낮은 신뢰도의 검색 결과를 LLM이 그럴듯하게
  포장할 가능성 자체를 원천 차단했다.

**실측 발견 — 화이트리스트 모델 중 실제로 못 쓰는 모델이 있었다.** 스펙 상
기본값이었던 `gemini-3.5-flash`를 실제로 호출해보니 재시도(간격을 두고 3회)해도
계속 503(high demand)만 반환됐다. 화이트리스트 6개 전부를 실측한 결과:
- `gemini-2.5-flash` → 404 (신규 사용자에게 더 이상 미제공, 사실상 폐기된 모델)
- `gemini-2.0-flash` → 429, quota limit **0** (이 계정 무료 티어에서 완전히 막혀있음)
- `gemini-3.5-flash` → 503 지속 (일시적 과부하라 보기 어려움)
- `gemini-3.6-flash` / `gemini-3.5-flash-lite` / `gemini-3.1-flash-lite` → 정상 동작

**기본 모델을 `gemini-3.6-flash`로 변경**했다(화이트리스트 자체는 6개 그대로 유지 —
안전 경계에는 문제가 없고 2개가 이 계정에서 죽어있을 뿐이라 화이트리스트에서 뺄
이유는 없음). 이 실측 결과는 `gemini_client.py`에 날짜와 함께 주석으로 남겼다.

### 3단계: `/api/query` 통합 검증

`generate_answer()`를 호출하고, `try/except`로 감싸 실패 시 `answer: null`,
`answer_error: "..."`로 응답하도록 통합했다(500 에러로 전체 요청이 죽지 않게).

2. 시뮬레이션: `unittest.mock.patch`로 `routes.query.generate_answer`가

   서버 검증 대체"가 아니다 — 실제 서버가 로드한 것과 동일한 `routes/query.py`

   호출 지점 하나뿐이다.)

### 발견 및 수정: 별표3(Table) 근거조항의 citation 포맷 버그

**증상**: 별표3(국외이주 목적 국외여행허가 기준표) 청크가 근거조항에 포함된 답변에서
"병역법 시행령 별표 3 **제별표3조** 제1항에 따르면..."처럼 어색하게 인용됐다. 사실을
지어낸 건 아니지만(hallucination 아님) citation 형식 요구사항("제○○조 제○항에
따르면")을 기계적으로 지키려다 생긴 포맷 오류.

**원인**: `_format_articles()`가 모든 결과에 `제{article_no}조` 템플릿을 무조건
적용했는데, 별표3 청크의 `article_no` 필드값은 숫자가 아니라 리터럴 문자열
`"별표3"`이라서 `제별표3조`라는 잘못된 조합이 생성됨.

**수정**: `article_no`가 `"별표"`로 시작하면 `제N조` 템플릿을 쓰지 않고
`{law_name} ({article_title}) 항목 {paragraph_no}` 형식으로 분기(`answer.py`).
system_instruction에도 "별표(표) 형태의 근거는 '○○ 시행령 별표 3에 따르면'처럼
표기하고 '제○○조'로 표기하지 말 것" 지시를 추가.

**재검증**: 클린 재시작 후 별표3이 포함된 쿼리 3개(아래 4단계 표의 #2/#3/#4) 전부
"병역법 시행령 별표 3에 따르면..." 형식으로 정상 인용됨을 확인.

### 실행 중 발견 — `gemini-3.6-flash`의 실제 무료 티어 일일 한도는 20회

원래 계획대로 `python3 evaluation/ragas_eval.py`를 실행했더니, reference-free
12개 평가 중 1개만 성공하고 나머지가 전부 `TimeoutError`로 실패했고
reference-based는 첫 job부터 바로 429가 났다:

```
ClientError(429 RESOURCE_EXHAUSTED. ... quotaId: 'GenerateRequestsPerDayPerProjectPerModel-FreeTier',
quotaDimensions: {'model': 'gemini-3.6-flash'}, quotaValue: '20' ...)
```

`gemini-3.6-flash`의 이 계정 실측 일일 한도가 **20회**였다 — Stage 5 설계 당시
가정했던 "일 1000~1500회"보다 훨씬 낮다. 오늘 세션에서 Stage 6 프로필 통합
테스트 + anchor 회귀 확인들로 이미 상당수를 써버린 상태였고, RAGAS의 파이프라인
실행(생성 6회) + judge 호출(대략 12~20회)을 더하니 순식간에 소진됐다. 직접
호출로 재확인해도 그 시점엔 이미 429였다.

**코드에 반영한 수정 2가지** (`evaluation/ragas_eval.py`):
1. **judge 모델을 생성 모델과 분리** — judge는 `gemini-3.5-flash-lite`(별도
   화이트리스트 모델, 별도 quota 버킷)를 쓰도록 `JUDGE_MODEL` 상수 추가.
   생성(`generate_answer()`)과 judge가 같은 모델의 같은 일일 quota를 두고
   경쟁하지 않게 됨.
2. **RAGAS 동시성을 직렬화** — RAGAS 기본값(`max_workers=16`,
   `max_retries=10`)은 무료 티어 RPM(10~15)을 훨씬 초과하는 동시 요청을
   쏴서, 진짜 429 몇 개가 `gemini_client.py`의 자체 백오프와 RAGAS 자체
   재시도가 겹치며 `TimeoutError` 폭탄으로 번졌다. `RunConfig(max_workers=1,
   max_retries=1)`로 직렬화해서 재발 방지.

### 오늘 실행 한정 임시 조치 — 생성 모델도 quota 소진으로 대체 (중요, 반드시 함께 읽을 것)

수정을 반영해도 `gemini-3.6-flash`(Stage 5의 실제 운영 기본값)는 오늘 quota가
이미 바닥나 있어서(재확인 결과 즉시 429), 오늘 하루치 결과를 얻으려고
**이번 실행 1회에 한해서만** `generation.answer.DEFAULT_MODEL`을
`unittest.mock.patch`로 `gemini-3.5-flash-lite`에 임시로 바인딩해서 돌렸다.
**코드베이스는 전혀 안 건드림** — `generation/gemini_client.py`의
`DEFAULT_MODEL`은 여전히 `gemini-3.6-flash` 그대로고, `/api/query`를 실제로
호출하면 지금도 `gemini-3.6-flash`로 답변이 생성된다.

**즉 아래 수치는 "지금 배포된 Stage 5 기본 모델(`gemini-3.6-flash`)의 실제
품질"이 아니라 "대체 모델(`gemini-3.5-flash-lite`)로 생성했을 때의 품질"이다.**
검색(retrieval) 쪽은 100% 실제 프로덕션 경로 그대로고, 생성 모델만 오늘의
quota 사정으로 바뀐 것 — 이 한계를 감안하고 아래 수치를 읽어야 한다.

### 수치 해석 시 반드시 감안해야 할 한계 (수치를 실제보다 깨끗하게 포장하지 말 것)

1. **ground_truth 4개는 독립적인 정답이 아니다.** 어제(7/31) Stage 5
   faithfulness 스팟체크에서 이미 조항 대조까지 검증됐던 실제 Gemini 응답을
   그대로 재사용한 것이다. 완전히 새로 작성한 gold answer가 아니라서
   순환적인 면이 있다 — 특히 context_recall(0.7917)은 "검색된 조항이
   ground_truth를 얼마나 커버하는가"를 재는데, 그 ground_truth 자체가 같은
   검색 결과를 보고 어제 생성된 답변이라서 점수가 실제보다 유리하게 나올
   가능성이 있다.
2. **오늘 실행분은 생성 모델이 대체됐다** (바로 위 섹션 참고) — faithfulness/
   answer_relevancy 0.28 안팎 점수는 `gemini-3.6-flash`가 아니라
   `gemini-3.5-flash-lite`가 생성한 답변을 채점한 결과다.
3. **faithfulness 0.28은 어제 수동 스팟체크(5/5 citation 정확, 조작 없음)와
   체감상 안 맞는다.** 원인을 여기서 확정하지는 못했다 — 가설로는 (a)
   RAGAS의 Faithfulness가 답변을 원자적 주장(claim) 단위로 쪼개 각각을
   retrieved_contexts와 대조하는데, 법조문 특유의 격식체 표현과 답변의
   패러프레이즈 사이 의미적 매칭을 lite 모델 judge가 엄격하게(또는 잘못)
   판단했을 가능성, (b) 애초에 lite 생성 모델의 답변이 어제 스팟체크한
   `gemini-3.6-flash` 답변보다 grounding이 실제로 약했을 가능성, 둘 다
   배제 못 함. 추가 조사 없이 "파이프라인이 27% 신뢰도로 환각한다"고
   해석하면 안 됨 — 어제 수동 검증(조항 번호 대조까지 마친) 쪽이 더 신뢰도
   높은 신호다.
4. **context_precision은 실패, 성공이 아니다.** NaN은 "정밀도가 나쁘다"가
   아니라 "4개 판정 시도가 전부 타임아웃나서 값 자체가 없다"는 뜻.

### 결론

6개 파일 적용, 리팩터링 회귀 없음 확인, RAGAS 파이프라인 자체는 실제로 끝까지
돌아가서 숫자를 냈다. 다만 (1) `gemini-3.6-flash` 일일 quota가 20회로 매우
낮다는 것, (2) 오늘 실행분은 생성 모델이 대체됐다는 것, (3) ground_truth의
순환성, (4) context_precision 미채점 — 이 네 가지 한계 때문에 오늘 나온 수치를
"이 파이프라인의 확정 품질 지표"로 쓰기는 이르다. 코드(judge 모델 분리,
RunConfig 직렬화)는 정상 상태로 남아있으니, `gemini-3.6-flash` quota가
초기화된 뒤(내일 이후) `python3 evaluation/ragas_eval.py`를 그대로(모델
패치 없이) 재실행하면 실제 운영 모델 기준 수치를 얻을 수 있다.
