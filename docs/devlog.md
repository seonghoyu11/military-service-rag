# DutyCompass - 개발자 노트: 해외체류 병역의무자 안내 RAG 챗봇

영주권자, 유학생, 이중국적자, 재외동포 2세 등 해외체류 병역의무자를 위한 RAG 기반 병역
행정절차 안내 챗봇 개발 기록. 단순 LLM 프롬프팅이 아니라 구조화된 파이프라인(파싱 →
임베딩 → 하이브리드 검색 → 재정렬 → 분류 → 생성)으로 정확도를 높이는 걸 목표로 했다.
스코프는 "병역의무 발생 ~ 입영 전"까지.

이 문서는 각 단계에서 뭘 만들었고, 뭐가 실제로 문제였고, 어떻게 검증했는지를 시간순으로
정리한 것이다. "한 번에 완벽하게 만들었다"가 아니라 "프로토타입을 만들어서 직접 써보고,
문제를 찾고, 데이터로 진단하고, 고쳤다"의 반복이었다는 걸 그대로 남겨두려 한다.

## 1단계: 법령 파싱 파이프라인

병역법·시행령·시행규칙·병무청훈령·국방부훈령·별표3까지 법령 PDF 6개를 조/항 구조를
유지하며 파싱해서 272개 청크로 만들었다. 원문 훼손 없이 그대로 보존하는 게 원칙이었고,
별표3(표 형태)는 행 단위로 자연어 문장으로 변환했다.

**샘플 검증 단계에서 실제로 발견한 버그 3가지:**
- `refers_to`(참조조항) 필드가 청크 헤더에 붙인 자기 조번호를 스스로 참조하는 것으로
  오인식 — 270개 중 224개(83%)가 오염돼 있었다. 헤더를 붙이기 전 본문에서만 참조를
  추출하도록 수정.
- PDF 추출 과정에서 단어 중간에 줄바꿈이 끼어드는 문제("사\n람" → "사람") — 582건.
  "한글+줄바꿈+한글" 패턴을 이어붙이는 함수(`join_wrapped_lines`)로 해결했는데, 이
  함수가 나중에 3단계 이후 세션에서 또 다른 버그의 원인이 된다(아래 참고).
- 별표3 표 셀 추출 시 공백이 끼어 카테고리 라벨이 깨지는 문제 ("병역준비 역, 사회복
  무요원...") — 공백 제거 후 비교하도록 수정.

## 2단계: 임베딩 모델 비교 + MongoDB 적재

BGE-m3 / multilingual-e5-large / KoE5 세 모델을 자체 제작 테스트셋(실제 케이스 기반
시나리오 + 병무청 FAQ 스타일 질문 15개, 그중 1개는 카투사 관련 의도적 네거티브 테스트)으로
Recall@K·MRR 비교했다.

**결과: BGE-m3 선정.** Recall@10 만점(14/14)이었고, 무엇보다 긍정/부정 질문 간 유사도
점수 구분이 가장 뚜렷했다 — multilingual-e5-large는 스코프 밖 질문에도 top1 유사도
0.801을 줘서 절대 점수만으로 "관련 조항 없음"을 판단하기 어려웠다. 흥미롭게도 한국어
특화 모델인 KoE5가 오히려 가장 낮은 성능을 보였는데, 이 규모(560M) 모델 간 우열은
"한국어 특화 여부"보다 retrieval 학습 방식·데이터 품질 차이가 더 크게 작용하는 것으로
보인다. 272개 청크를 BGE-m3로 임베딩해서 MongoDB Atlas Vector Search에 적재했다.

## 3단계: Hybrid Retrieval + Reranker

BM25(`kiwipiepy`로 형태소 분석 후 조사/어미 제거) + Dense(BGE-m3) 점수를 min-max
정규화 후 가중합. 그리드서치로 `alpha=0.3`(BM25 70% + Dense 30%)이 최적으로 나왔다 —
Recall@5/10 만점, MRR 0.929.

여기서 흥미로운 발견 하나: **BM25 단독으로도 이미 Recall@5/10 만점**이었다. 이 도메인
(병역법 Q&A)은 사용자 질문과 법조문이 어휘를 상당히 공유하기 때문으로 보인다. 그리고
2단계 임베딩 비교 때 3개 모델이 전부 놓쳤던 질문("출국을 미루거나 기피하면 어떤
불이익")을 BM25가 정확히 잡아냈다 — 정답 조항에 "기피"라는 단어가 그대로 들어있는데도
dense 임베딩은 놓쳤던 케이스라, 하이브리드 설계가 실제로 필요하다는 근거가 됐다.

Reranker(bge-reranker-v2-m3)는 이 작은 테스트셋에서 Recall/MRR을 더 올리진 못했지만,
**점수의 해석 가능성**에서 결정적으로 유리했다 — 실제 정답 질문엔 0.77~0.999, 스코프
밖 질문엔 0.000을 줘서 "관련 조항 없음" 판단에 쓸 수 있는 신뢰도 점수를 제공했다.

## 4단계: Intent Classifier

처음엔 rule-based 키워드 매칭으로 시작 (데이터 쌓이면 경량 분류기로 교체할 구조로 설계).
유저타입(영주권자/유학생/이중국적자/재외동포2세) × 주제(연기/허가취소/영리활동 등)로
분류.

**중요한 스코프 결정**: 카투사/어학병은 모집병이라 스코프("입영 전까지") 자체엔 들어가지만,
지원자격(TOEIC 점수 등)이 법조문이 아니라 매년 바뀌는 병무청 모집공고 성격이라 데이터셋에서
의도적으로 제외했다. 관련 훈령을 제대로 넣으려면 준용조항이 줄줄이 딸려와서 스코프가
무한정 커지는 문제도 있었다. 대신 intent classifier에서 카투사/어학병 키워드를 감지하면
실제 병무청 모집공고 링크(카투사/어학병 각각 다른 페이지)로 안내하고, 유저타입이 같이
감지되면 스코프 안에서 답변 가능한 인접 정보(영주권자 등 입영희망신청제도, 제24조)로
자연스럽게 유도하도록 구현했다.

## 프로토타입을 만들고, 직접 써보고, 문제를 찾다

여기서부터가 사실 제일 많이 배운 구간이다. Flask API(`app.py`, `routes/query.py`) +
순수 HTML/JS 프로토타입(`frontend/prototype.html`)을 빠르게 만들어서, Claude API 연동
없이도 "분류 → 검색 → 재정렬"까지의 파이프라인을 실제로 눈으로 확인할 수 있게 했다.
그리고 실제 질문을 넣어보면서 코드만 봐서는 절대 못 찾았을 문제들이 계속 나왔다.

### 발견 1: 검색 결과에 반대 의미가 뜬다

"영주권자인데 입영연기 어떻게 하나요"를 넣었더니, "병역연기 처분을 **취소**한다"는
정반대 의미의 조항(자진 조기입영 제도)이 1위로 떴다. 진단해보니:
- 조문 헤더에 "국외여행의 허가 **및 취소**"처럼 제목 자체에 "취소"가 들어있어서, 그
  조의 모든 항이 실제 내용과 무관하게 "연기+취소" 동시출현으로 오염되고 있었다.
- 더 근본적으로: intent classifier가 계산한 태그가 실제 검색 랭킹에 전혀 반영되지
  않고 있었다 — 화면 표시용 메타데이터에 그쳤다. 태그를 아무리 정교하게 고쳐도 검색
  결과 자체는 안 바뀌는 구조였다.

"연기" 토픽을 `입영연기_신청`(허가로 인해 연기되는 근거)과 `입영연기_취소`(연기 처분
자체가 취소되는 조항) 두 방향으로 분리하고, 정밀한 정규식(`연기...취소` 근접 매칭,
"연기"+"취소" 단순 동시출현보다 훨씬 좁게)으로 코퍼스를 재태깅했다. 그리고
`routes/query.py`에 실제 가중치를 반영해서 intent 방향과 청크 방향이 일치하면 부스트,
불일치하면 패널티를 주도록 구현했다. 이후 재검증에서 반대 방향 질문("취소하고 싶어요")도
정확히 반대로 부스트되는 걸 확인했다.

### 발견 2: 태그를 아무리 고쳐도 검색 결과가 그대로다

발견 1의 수정을 반영하고 재테스트했는데, "언제까지 입영 안 해도 되나요" 같은 질문이
`topic_tags: ['일반']`로 분류되고 있었다 — "연기" 관련 키워드가 하나도 안 걸려서
방향성 보정 로직 자체가 발동을 안 했던 것. 콜로케이션(구어체 표현)이 법률 용어와 얼마나
다른지 계속 확인하는 과정이었다: "언제까지", "몇 살까지", "나이 제한" 같은 표현은
"연기"라는 단어를 전혀 안 쓰면서도 정확히 연기 관련 질문이다.

### 발견 3: 조문 경계가 통째로 깨져 있었다

원본 `law_chunks.json`을 직접 열어보다가, 국외여행 업무처리 규정 제21조 청크에 실제로는
제21~23조 세 조문이 경계 구분 없이 병합된 걸 발견했다 ("...재학하는 경우제22조(영리활동의
범위)..."처럼 공백도 없이 이어붙음). 272개 청크 전수 스캔 결과 **16개가 이렇게 오염돼
있었다**.

원인을 추적해보니, **1단계에서 만든 줄바꿈 복구 함수(`join_wrapped_lines`)가 조문 경계의
정당한 줄바꿈까지 지워버린 부작용**이었다. 원본 PDF엔 조문이 바뀌는 지점에 정상적으로
줄바꿈이 있었는데, "한글+줄바꿈+한글이면 무조건 붙인다"는 규칙이 이 경계까지 뭉개버린
것. 한 가지 버그를 고치려고 만든 로직이 나중에 다른 층위에서 새 버그를 만들어낸 사례라
기록해둘 만하다. 줄바꿈 복구 로직에 "제N조(" 패턴 앞은 붙이지 않는 예외를 추가하고,
전체 재파싱 → 재태깅 → 재임베딩 → MongoDB 재색인까지 다시 돌렸다 (272개 → 270개 청크).

### 발견 4: 정답이 코퍼스에 있는데 검색이 못 찾는다

"휴학하면 입영연기가 취소되나요", "자퇴하면 병역은 어떻게 되나요" — 정답 조항(재학
사실을 확인한 결과 허가요건을 유지하지 못한 경우 → 허가취소)이 "휴학"/"자퇴"라는 단어를
전혀 안 쓰고 있어서, "자퇴" 질문은 BM25 순위가 270개 중 168위까지 밀렸다.

특정 동의어(휴학/자퇴/제적)를 감지하면 해당 조항을 후보 풀에 강제로 넣는 방법을 먼저
시도했는데, 그래도 top-5에 안 나타났다. 더 파보니 **리랭커(cross-encoder) 자체가
"휴학"과 법조문 표현 사이의 의미 연결을 약하게 판단**해서, 후보 풀에 이미 있었는데도
top-15 리랭크 컷 이전에 탈락하고 있었다. 후보 풀에 넣는 것만으론 부족했던 것 —
리랭커가 전체 후보에 점수를 매기게 하고, 앵커 매칭 시 명시적 부스트를 추가로 줘야 했다.

### 발견 5: 정답과 노이즈의 점수가 뒤바뀔 수 있다

"검색 결과가 관련 없어 보이면 확신도 낮음을 표시해달라"는 요구에 threshold를 구현하려고
실제 점수 분포를 찍어봤는데, **진짜 정답 케이스(0.0061)가 노이즈 케이스(0.0147)보다
낮은 점수**를 받는 역전 현상을 발견했다. 문장이 짧고 불완전하면(질문형이 아닌 진술문)
재랭커가 점수를 낮게 주는 경향이 있어서, 단일 절대 threshold로는 이 둘을 깔끔하게
분리할 수 없다는 걸 데이터로 확인한 것.

여기서 내린 판단: hard cutoff(결과를 숨김)이 아니라 어드바이저리 방식(낮은 점수면
"확신도 낮음" 표시는 하되 결과는 그대로 보여줌)으로 구현했다. 완벽한 신호가 없다는 걸
인정하고, 약한 신호의 정답까지 숨기는 것보다는 과실 표시 몇 번을 감수하는 쪽을 택한
것이다.

### 발견 6: 스코프 판정에 사각지대가 있었다

"군대 갔다 온 사람이 다시 영주권 취득하면 어떻게 되나요" 같은 **전역 이후** 시점 질문은
카투사/어학병 키워드에 안 걸려서, fallback 없이 관련도 0.05~0.16대의 노이즈성 결과가
정상 답변처럼 노출됐다. "전역", "제대", "갔다 온" 등 입영-이후 시점 표현을 감지하는
별도 키워드군을 만들어서, 카투사 fallback(모집공고 안내)과는 다른 문구("이 챗봇은
입영 전 절차만 다룹니다")로 분기하도록 추가했다.

### 발견 7: 코드는 맞는데 서버 응답이 다르다

발견 6을 고치고 나서 다시 테스트했는데, 분류기 코드를 독립적으로 실행하면 정확히 동작하는데
실제 API 응답은 옛날 동작을 보이는 상황이 발생했다. 원인은 파일이나 로직이 아니라
**배포 프로세스 관리**에 있었다 — 이 세션에서 서버를 여러 번 재시작하면서 포트 기준으로만
(`lsof -ti:5001 | xargs kill -9`) 프로세스를 죽였는데, Flask의 auto-reloader가 부모
감시 프로세스 + 자식 워커 프로세스 구조라 포트를 문 자식만 죽이고 부모가 좀비로 남는
경우가 있었다. 옛날 코드를 물고 있는 좀비 프로세스가 요청을 처리하고 있었던 것.

재발 방지로 서버 시작 시 로그에 "지금 이 프로세스가 청크 몇 개, 어떤 코드 버전을
로드했는지"(`law_chunks.json` 청크 개수 + mtime, 특정 키워드 리스트의 해시)를 한 줄
찍도록 추가했다. 그리고 재시작 습관 자체를 포트 기준(`lsof`)에서 프로세스명 기준
(`pkill -f "app.py"`)으로 바꿨다.

  도움이 됐다.
- **완벽한 threshold는 없을 수도 있다.** 데이터가 그렇게 말하면 인정하고, hard cutoff

- **프로토타입을 만들어서 직접 써보는 게 제일 빠른 QA다.** 이번 세션에서 나온 버그의
  대부분은 코드 리뷰만으로는 안 보였고, 실제 질문을 넣어봐야 드러났다.
- **배포/프로세스 관리도 디버깅 대상이다.** "코드는 맞는데 결과가 이상하다"의 상당수는
  코드가 아니라 어떤 프로세스가 실제로 요청을 처리하고 있는지의 문제였다.

## 5단계 대기 중: threshold 실험과 회피 표현 갭 하나 더 (2026-07-15)

Claude API 키 발급 대기가 길어지는 김에, 이슈 2(threshold)에서 남겨뒀던 숙제와 스트레스
테스트에서 나온 의심 사례 하나를 마저 point했다.

**margin(top1-top2) 실험.** 절대 점수 하나로는 정답/노이즈를 못 가른다는 게 이슈 2의
결론이었는데, "1위가 2위를 얼마나 크게 앞서는가"가 더 나은 신호일 수 있다는 가설을
세우고 `routes/query.py`에 margin 로깅을 추가해 12개 재검증 쿼리로 실측했다. 결과는
반쪽짜리 성공: 애초에 문제였던 역전 케이스(정답 0.0061 < 노이즈 0.0147)를 margin
기준으로 다시 보면 순서가 바로잡히긴 하는데(0.0008 > 0.0006), 그 격차가 0.0002
수준이라 노이즈 샘플 단 2개로 실전 threshold를 확정하기엔 근거가 너무 얇았다. 강한
정답 케이스는 애초에 기존 절대 threshold로도 충분히 걸러지고 있어서 margin이 거기서
얻는 추가 이득도 없었다. 그래서 코드는 안 건드리고 로깅만 프로덕션에 남겨서 데이터를
계속 쌓기로 했다 — "가설의 방향은 맞는데 지금 가진 데이터로 액션을 걸기엔 이르다"는
것도 정답의 한 형태라는 걸 다시 확인한 케이스.

**회피 표현 갭.** "시민권 있는데 그냥 한국 안 들어가면 안 되나요" 같은 질문이
`topic_tags: ['일반']`로 빠지고 top1 관련도 0.0123(사실상 노이즈)으로 나온다는 의심이
있었다. 재검증해보니 실제로 재현됐고, 원인은 익숙한 패턴이었다 — "안 들어가면"/
"귀국 안 하면" 같은 표현이 "기피"/"위반" 같은 법률 용어를 전혀 안 쓰기 때문에
`제재` 토픽 키워드에도, BM25/dense 후보 풀에도 안 걸렸다. `TOPIC_KEYWORDS["제재"]`에
회피 동사 표현을 추가하고, "휴학/자퇴" 때 썼던 것과 같은 anchor 강제포함 패턴으로
병역법 제70조(국외여행허가 의무)·제94조(그 의무 위반 시 처벌)를 연결했다. 재검증
결과 top1이 제94조로 바뀌고(boosted score 0.30) `low_confidence`도 정상적으로
`False`로 떨어졌다.

이 과정에서 부수적으로 확인한 것: intent classifier가 `out_of_scope=True`를 반환하는
질문(카투사, 전역 이후 시점 등)은 reranker 자체가 호출되지 않아서 margin 로깅이
발동하지 않는다 — margin 데이터를 모을 때 이 분기를 감안해야 한다.

## 5단계 LLM 전환: Anthropic Claude → Google Gemini (2026-07-31)

Claude API는 사용하려면 결제수단 등록(선결제 크레딧)이 필요해서 개발 착수가 계속
미뤄지고 있었다. Google Gemini API(Google AI Studio, `GOOGLE_API_KEY`)는 카드 등록
없이 무료 티어로 바로 개발을 시작할 수 있어서 5단계 LLM을 Gemini Flash로 전환하기로
결정했다.

이 전환이 리스크가 낮다고 판단한 근거: 이 프로젝트의 "판단" 역할(유저타입/의도 분류,
근거조항 검색·랭킹, 신뢰도 판정)은 이미 4단계까지의 rule-based 파이프라인이 전담하고
있고, LLM은 검색된 근거조항 텍스트를 citation과 함께 자연어로 종합·생성하는 역할만
맡는다. 즉 모델 교체가 정확도의 핵심 로직에는 영향을 주지 않고, 생성 품질(문장 자연스러움,
citation 형식 준수, grounding 충실도)만 재검증하면 되는 구조라 전환 비용이 작다.

무료 티어 특성상 과금이 발생하면 안 된다는 제약이 새로 생겨서, 모델명 화이트리스트
하드코딩(`gemini-3.6-flash`/`gemini-3.5-flash`/`gemini-3.5-flash-lite`/
`gemini-3.1-flash-lite`/`gemini-2.5-flash`/`gemini-2.0-flash` 6개만 허용, Pro 계열
차단), Vertex AI 경로 미사용(Google AI Studio 경로만), rate limit 초과 시 무한 재시도
대신 최대 재시도 횟수 제한 같은 안전장치를 코드에 넣었다. 기본 모델은 화이트리스트
6개를 실제로 호출해본 결과(2개는 이 계정에서 404/quota 0으로 사실상 사용 불가)를
반영해 `gemini-3.6-flash`로 정했다. 상세 구현·검증 결과는 `docs/eval_results.md`의
"Stage 5: Gemini Flash 답변 생성 검증" 섹션 참고.

## 6단계: Flask API 정식화 + RAGAS 정량 평가 (2026-08-01)

로그인 없는 경량 세션 프로필(`/api/profile`)과 피드백 수집(`/api/feedback`)을
붙였다. 세션 프로필은 매번 "저는 영주권자인데..."를 다시 안 쳐도 되게 하는
순수 UX 편의 기능이라, `intent["user_type_tags"]`에만 영향을 주고 검색 랭킹
로직 자체는 안 건드리도록 설계했다 — `classify()`에 `session_user_type`
파라미터를 추가하되, 질문 텍스트에서 유저타입이 명시적으로 감지되면 그게 항상
세션 프로필보다 우선하게 했다(질문이 제3자 얘기를 할 수도 있으니까).

이어서 RAGAS 정량 평가를 붙였다. `/api/query` 뷰 로직을 `answer_question()`
순수 함수로 분리해서, RAGAS가 HTTP 없이 이 함수를 직접 호출해 실제 프로덕션
코드 경로 그대로 평가하게 했다 — 이전 세션의 `answer_error` monkeypatch
검증과 같은 철학이다. RAGAS의 LLM judge도 `langchain_google_genai`를 직접
꽂지 않고 `gemini_client.generate()`를 경유하는 커스텀 `BaseChatModel`로
감싸서, judge 호출도 이 프로젝트의 "절대 과금 안 됨" 화이트리스트/backoff를
그대로 통과하게 했다.

**여기서도 실행해보고서야 알게 된 것 두 가지:**
- `ragas==0.4.3`이 이 프로젝트가 안 쓰는 Vertex AI 통합
  (`langchain_community.chat_models.vertexai`)을 무조건 import하는데, 그
  서브모듈이 최신 `langchain-community`(0.4.2, "sunset" 진행 중)에는 이미
  제거돼 있어서 `import ragas` 자체가 깨졌다. `langchain-community==0.3.31`로
  고정해서 해결.
- `gemini-3.6-flash`의 이 계정 실측 일일 quota가 **20회**였다 — Stage 5
  설계 당시 가정했던 "1000~1500회"보다 훨씬 낮다. 오늘 세션의 프로필 통합
  테스트 + anchor 회귀 확인만으로 이미 상당수를 써버린 상태에서 RAGAS의
  생성 6회 + judge 호출(12~20회 안팎)을 더하니 순식간에 소진돼서, 첫 실행은
  1/12 평가 성공 후 나머지가 전부 quota 관련 에러로 실패했다. judge 모델을
  생성 모델과 다른 화이트리스트 모델(`gemini-3.5-flash-lite`)로 분리하고
  RAGAS 동시성을 직렬화(`max_workers=1`)한 뒤 재시도해서 실제로 끝까지
  돌리는 데 성공했다 — 다만 그날 하루는 `gemini-3.6-flash` 자체도 이미
  quota가 바닥나 있어서, 오늘 실행분의 실제 답변 생성은 코드 변경 없이
  `unittest.mock.patch`로 생성 모델만 임시로 `gemini-3.5-flash-lite`에
  묶어서 얻은 수치다.

나온 수치(faithfulness 0.2778, answer_relevancy 0.2670, context_recall
0.7917, context_precision은 타임아웃으로 NaN)는 그래서 "확정 품질 지표"로
보기엔 이르다 — 상세 한계와 재실행 방법은 `docs/eval_results.md`의 "Stage 6"
두 섹션 참고.

## Stage 5 기본 모델을 lite로 전환 시도했다가 롤백 (2026-08-03)

Google AI Studio 콘솔 실측으로 화이트리스트 6개 모델의 RPD가 균일하지
않다는 걸 발견했다 — "Flash" 계열(3.6/3.5/2.5-flash)은 전부 RPD 20인데
"Flash Lite" 계열(3.5/3.1-flash-lite)만 RPD 500이었다. 당시 기본값
`gemini-3.6-flash`는 이미 하루치 20회를 다 써버린 적이 있어서, 데모 중
quota 소진 위험을 줄이려고 `DEFAULT_MODEL`을 `gemini-3.5-flash-lite`로
바꿔봤다.

바꾸고 나서 7/31 faithfulness 스팟체크와 동일한 5문항을 재실행해봤더니,
5개 중 2개(휴학 관련 질문, 사회복무요원 해외여행 질문)에서 검색 결과에
정답 조항이 명확히(특히 후자는 top1 점수 0.9882) 들어있는데도 lite 모델이
그걸 전혀 인용하지 않고 "제공된 조항만으로는 판단하기 어렵습니다"라는
회피 답변만 냈다. 재현성 확인을 위해 두 질문을 각각 2번씩 더 재시도했는데
3/3 전부 동일했다 — 샘플링 노이즈가 아니라 lite 모델의 실제 결함이었다.
hallucination은 아니지만(근거를 지어낸 게 아니라 무시한 것) "정확한 조항
인용"이라는 핵심 가치를 못 지키는 건 마찬가지라, `gemini-3.6-flash`로
롤백했다. 롤백 후 같은 두 질문을 재검증하니 인용이 baseline 수준으로 완전히
복구됐다.

이 참에 quota가 리셋된 상태에서 RAGAS도 model patch 없이 (진짜
`gemini-3.6-flash` 기준으로) 다시 돌렸다. faithfulness가 7/31의
0.2778에서 **0.8783**으로 크게 뛰었는데, 이건 7/31에 세워뒀던 가설 — 그날의
낮은 점수가 파이프라인 결함이 아니라 임시로 대체했던 lite 생성 모델 자체의
문제였을 것이라는 — 이 맞았다는 걸 뒷받침한다. context_precision은 이번에도
타임아웃(NaN)으로 채점 실패했지만, 429/quota 에러는 전혀 없었다 — 오늘
3.6-flash 호출 총 8회(롤백 검증 2회 + RAGAS 생성 6회)로 RPD 20 한도 안에서
끝남. `DEFAULT_MODEL`은 `gemini-3.6-flash`로 유지, RPD 20 리스크는 알고
감수하는 걸로 정리했다. 전체 표/로그는 `docs/eval_results.md`의 새 섹션
참고.

## 7단계: Next.js 프론트엔드 포팅 (2026-08-04)

Claude Design 프로토타입(`DutyCompass.dc.html` — 전용 런타임 위에서
목업 데이터로 동작하던 완성 UI)을 Next.js(App Router) + TypeScript +
Tailwind CSS로 포팅하고, 목업 대신 실제 `/api/query`에 연결했다. 시작
전에 plan mode로 들어가서 계획부터 세웠다 — 새 앱 전체를 스캐폴딩하는
큰 작업이라 코드부터 짜지 않고 구조를 먼저 정리한 게 맞았다.

**설계 결정 중 계획 단계에서 이미 확정한 것들**:
- 테마 시스템은 원본 그대로 CSS 커스텀 프로퍼티 inline 주입 방식 유지
  (Tailwind `dark:` 클래스로 옮기면 ~90개 색상값을 두 곳에 손으로
  옮겨적어야 해서 오류 위험만 커짐).
- next-intl은 `app/[locale]/` 라우팅 구조까지만 지금 잡고, 실제 영문

- 로딩 애니메이션은 실제 네트워크 응답 시간이 가변적이라, 4단계를

## 8단계: `/api/query` 응답 지연 진단 — 재랭커가 진짜 병목이었다 (2026-08-04)

사용자가 셸 로그에서 확보한 단서 하나로 시작했다: 특정 요청 처리
도중에만 "Loading weights"가 다시 찍혔고, 같은 프로세스의 그 전 두
요청에선 안 찍혔다는 것. 임베더(BGE-m3)/reranker가 매 요청 재로딩되고
있는 게 아니냐는 가설을 세우고 검증부터 요청받았다.

검증해보니 가설은 틀렸다 — `embedder.py`/`reranker.py` 둘 다 이미
모듈 레벨에서 정상적으로 캐싱하고 있었다(`_loaded_models` dict, `_model`
전역). 진짜 원인은 `answer_question()`이 `out_of_scope`(카투사류)면
검색/재랭크를 아예 안 타고 조기 리턴하는 구조였다 — 그래서 두 모델은
프로세스의 **첫 in-scope 요청**에서 처음 lazy-load된다. 세션의 첫 두
질문이 out-of-scope였고 세 번째가 처음으로 in-scope 질문이었다면,
관찰된 로그와 정확히 들어맞는다. 버그가 아니라 "누가 cold-start
비용을 떠안느냐"의 문제였던 것.

그래도 실사용자 입장에선 여전히 문제라(재시작 후 첫 진짜 질문이
느려짐), `app.py`에 `_preload_models()`를 추가해 서버 기동 시점에
미리 로드하도록 고쳤다. 원인 진단과 별개로, 앞으로 "느리다"는 게
어느 단계 문제인지 바로 알 수 있게 `answer_question()`에 `[timing]`
로그(retrieval/rerank/generate/total)도 추가했다.

**여기서 진짜 발견이 나왔다.** 클린 재시작 후 실측해보니, preload
수정으로 "Loading weights" 재발은 완전히 사라졌는데도 요청 하나가
여전히 56~94초가 걸렸다. `[timing]` 로그로 단계를 쪼개보니 **재랭커가
43~73초, 전체의 75~80%**를 먹고 있었다 — retrieval(~7초)이나
generate(5~15초)와는 비교가 안 되는 크기. `routes/query.py`엔 이미
"재랭커가 최대 50개 후보를 top_k 절삭 없이 매번 CPU로 스코어링하는
구조라 병목일 수 있다"는 주석이 있었는데, 이번 실측으로 그 가설이
확정됐다. 결과적으로 처음 의심했던 "모델 재로딩"은 진짜 원인이
아니었고, 코드에 이미 적혀 있던 다른 가설이 진짜였다 — 타이밍 로그를
추가하지 않았다면 계속 "cold-start 문제"로 오인한 채 넘어갔을
부분이다.

이번엔 진단과 계측(preload + timing 로그)까지만 하고 재랭커 자체는
건드리지 않았다. 상세 수치와 코드는 `docs/eval_results.md` "Stage 8"
참고.

## 8단계 후속 1: reranker 배치/스레드 튜닝 시도 — 개선 없음 (2026-08-04)

8단계 결론("재랭커가 진짜 병목")을 이어받아, 실제로 손댈 수 있는지
확인하는 라운드. 계획은 두 가지였다: (1) `rerank()`가 후보 쌍마다
`predict()`를 개별 호출하는 루프면 배치 호출로 바꾸기, (2) 그래도
느리면 CPU 스레드 수를 늘려보기.

1번은 열어보니 이미 `model.predict(pairs)` 한 번으로 전체 후보를
넘기고 있었다 — 고칠 게 없었다. 2번으로 넘어가서 확인해보니
`torch.get_num_threads()`가 4인데 이 머신(M3)은 논리 코어가 8개였다.
`reranker.py`에 `torch.set_num_threads(os.cpu_count())`를 모듈
최상단에 추가했다.

anchor 3개(휴학→27조③ 0.5618, 아르바이트→22조 0.3002, 언제까지→별표3
0.3092) 점수는 스레드 수 변경 전후로 소수점까지 완전히 동일 — 회귀
없음 확인. 그런데 `[timing]` 로그로 4개 쿼리를 재실행해보니 rerank
시간이 47.55→52.25s, 73.11→72.19s, 72.67→72.40s, 42.68→40.69s로
사실상 그대로였다(한 건은 오히려 악화). 결론: 이 두 가지 시도 모두
효과가 없었다. bge-reranker-v2-m3 한 번의 forward pass가 스레드 4개로도
이미 포화 상태였거나, 스레드를 늘린다고 선형으로 빨라지는 연산이
아닌 것으로 보인다. 코드는 무해하니 남겨뒀지만 병목 해결책으로
검증되지는 않았다. 상세 수치는 `docs/eval_results.md` "Stage 8 후속"
참고.

## 7단계 후속: OOS 응답 화면 수정 2건 (2026-08-04)

"카투사 지원하고 싶은데 영주권자도 되나요?"로 실제 테스트하다가
발견한 문제 2건을 고쳤다: (1) OOS 안내문 안의 병무청 링크가 평문이라
클릭이 안 됨, (2) `relatedScopeInfo` 근거 카드가 항상 펼쳐진 채로
나와서 정작 안내 메시지가 화면에서 밀려남.

링크화는 백엔드 포맷을 바꾸지 않고 프론트 표시 레이어에서만 처리하기로
했다 — `mapAnswerSegments`와 같은 패턴으로 `linkifyText()`를 추가해서
텍스트를 text/link 세그먼트로 쪼갰다. 처음엔 URL을 `\S+`로 통짜로
매칭한 뒤 트레일링 문장부호만 사후에 잘라내는 방식으로 짰는데,
"공고(https://...)를 확인하세요"처럼 괄호로 감싼 링크에서 실패했다
— 닫는 괄호 뒤에 공백 없이 바로 이어지는 텍스트("...0525)를")까지
전부 URL로 삼켜버렸다. 유닛 테스트를 먼저 6개 써두고 돌려봐서 잡아낸
버그였다 — 눈으로 코드만 봐서는 못 잡았을 케이스. `)`를 URL 문자
집합에서 아예 제외하는 방식으로 고쳤다. 부수적으로, 백엔드 메시지가
`\n`으로 여러 줄을 구분해서 보내는데 프론트가 그 줄바꿈을 렌더링에
반영 안 하고 있던 것도 발견해서 `whiteSpace: pre-line`으로 같이
고쳤다.

토글은 `MessageItem.tsx`의 기존 패턴(로컬 `useState` +
`EvidenceToggleButton` + 조건부 카드 리스트)을 `OosCard.tsx` 안에
그대로 재현했다. `EvidenceToggleButton`이 `evidence` 네임스페이스를
하드코딩하고 있었길래 `namespace` prop을 추가해서 재사용 — 새로
컴포넌트를 안 만들어도 됐다.

Playwright 헤드리스 브라우저로 실제 검증: 카투사 질문에서 링크 클릭
가능/토글 펼침·숨김 정상 동작 확인, `related_scope_info: null`인
케이스(유저타입 미감지)에서 빈 토글 버튼이 안 뜨는 것 확인,
`isNormal`/`low_confidence` 기존 토글 동작에 회귀 없음 확인 — 전부
콘솔 에러 0건. `vitest`(19/19)·`tsc --noEmit`·`eslint` 전부 통과.
상세 검증 로그와 스크린샷 설명은 `docs/eval_results.md` "Stage 7 후속"
참고.

## 9단계: EN 토글 실제 동작 구현 — 영문 답변 생성 (2026-08-05)

7단계에서 next-intl 라우팅만 잡아두고 EN 버튼은 "준비 중" 툴팁
스텁이었던 걸, 실제로 (1) UI 전체 영문화 (2) Gemini 답변 본문 영어
생성 (3) 법조문 인용은 한국어 원문 유지, 세 가지가 동작하도록
만들었다.

`language` 파라미터를 `answer_question()` → `classify()` →
`generate_answer()`로 배선하고, 백엔드 고정 문자열(OOS 안내, 저신뢰
안내)은 전부 `{"ko":..., "en":...}` 딕셔너리로 통일했다.

프론트는 `Header.tsx`가 next-intl의 `useRouter`/`usePathname`으로
실제 locale 전환(`router.replace(pathname, {locale})`)을 하도록
바꾸고, 기존 "준비 중" 스텁 메커니즘(`showEnHint`/`tryEn`/
`EN_HINT_MS`)은 완전히 제거했다. `messages/en.json`도 지금까지
`ko.json` 복사본이던 걸 실제 영문으로 교체.

가장 까다로웠던 건 `citation_parser.py`가 한국어 정규식 트리거
("...에 따르면")로 답변을 파싱한다는 점이었고, 여기서 두 번
잘못짚었다. 1차: 영문 답변이 이 문구를 "알아서" 재현해줄 거라
기대하지 않고 EN system instruction에 "이 정확한 한국어 문구를
영어 문장 속에 그대로 넣어라"라고 못박았다 — 파싱은 잘 됐지만
실제 답변을 읽어보니 `"According to X에 따르면"`처럼 "according
to"를 두 언어로 중복 표기하고 있었다. 2차: 영어 전치사 없이
"X에 따르면, ..."로 문장을 바로 시작하게 고쳤는데, 사용자가 다시
지적 — "영어 버전이면 according to만 있고 '~따르면'은 아예 있으면
안 된다"는 게 진짜 요구사항이었다. 결국 `citation_parser.py`에
EN 전용 정규식("According to {법령명} Article N, Paragraph M")을
새로 추가하고 system instruction도 "에 따르면"을 EN 답변에서
완전히 금지하는 쪽으로 다시 썼다. 두 번 다 파싱 자체는 처음부터
문제없었고, 실패는 항상 "파싱은 되지만 스펙과 다른 문장" 쪽이었다
— 자동 검증만으로는 못 잡고 사람이 실제 답변을 읽어야 잡히는
종류의 문제였다.

검증 도중 MongoDB Atlas 연결이 TLS 핸드셰이크 단계에서 통째로
막히는 일도 있었다(작업과 무관한 인프라 이슈 — IP 허용 목록 갱신
후 해결). 그 전까지 Mongo가 필요 없는 부분(`classify()` 언어 분기,
pytest, 프론트 tsc/eslint/vitest)부터 먼저 확인해두고, 연결 복구
후 EN 정상(별표 출처·일반 조항 출처 둘 다)/low_confidence/
out_of_scope + 같은 질문 KO 회귀를 실제 HTTP로, EN 토글 버튼
자체는 Playwright로 마저 확인했다 — 전부 정상, 콘솔 에러 0건.
상세 내용은 `docs/eval_results.md` "Stage 9" 참고.
